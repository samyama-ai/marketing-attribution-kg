# Dataset Card — Marketing Attribution KG

A measurement ledger as a graph: every read a brand takes about its own
marketing held as a claim, with the run that produced it, the dataset that run
consumed, and the source that dataset came from.

## ⚠️ The data is synthetic. Read this first.

**Nothing in this graph is a real brand's data.** The periods, products, markets,
channels, methods, runs, studies and claims are all generated by
[`data/generate.py`](data/generate.py). There is no client, no licensed feed and
no scraped source anywhere in it.

**The findings were planted.** The fifteen things the question catalogue
surfaces — a booked number with no traceable source, two methods agreeing off
one shared dataset, a decision taken on evidence since superseded — were written
into the generator on purpose.

So this repo does not demonstrate a discovery. **It demonstrates that the
structure finds a known defect without being told where to look**: the questions
are answered by traversal over the schema, not by a query that names the row it
is looking for. Whether that generalises to a real measurement programme is
exactly the thing this cannot tell you, and the reason to treat it as an
argument about shape rather than evidence about any brand.

What *is* real: the schema, the question set, the Cypher, the engine behaviour
and every figure below.

### Why `Claim` is 19,716 of 20,102 nodes

A claim is one method's read of one thing in one period, and the graph carries
eight quarters of them at several grains — channel, channel+product,
channel+market and channel+segment. Market-level claims alone account for most
of it, because there are 210 markets. That shape is deliberate: the
questions about corroboration and disagreement only mean something when the same
channel has been measured many times, by different methods, at different grains.

The consequence worth knowing: `ABOUT` at 39,166 and `FOR` at
19,740 are most of the edge count, and both hang off claims. A query that
starts at a claim and walks outward is cheap; one that starts by pairing claims
is not, which is what the front page's hero query is about.

## Provenance — how it was built

| stage | what runs | what it produces |
|---|---|---|
| generate | `python data/generate.py` | the CSVs under `data/csv/`, gitignored |
| verify | `python data/verify_data_coverage.py` | refuses if a planted finding is absent |
| load | `python etl/load.py --url ...` | the graph in a running engine |
| measure | `python -m etl.probe_readme --record` | the committed record every figure is read from |

The record carries the commit it was measured at and a `dirty` flag, and
[`tests/test_readme.py`](tests/test_readme.py) refuses a record produced from an
uncommitted tree — a commit that cannot reproduce its own numbers is not
provenance.

## Known limitations

**Schema properties the generator never emits.** `currency`, `booked_on` and
`booked_by` on `PLLine`; `committed_on` on `Spend`; `action`, `actor` and
`amount_moved` on `Decision`; `treatment_markets`, `control_markets` and
`matched_on` on `GeoTest`; `confidence` on `Claim`. `booked_on` is the
load-bearing one — comparing it against `Run.executed_on` is how a real booking
is told from a backfill, and that question cannot be asked here yet.

**Data loaded but never queried.** The 210 `Market` nodes, `GeoTest.mde`,
`Run.observed_from` / `observed_to`, `IN_CYCLE`, `DUE_FOR`, `EXECUTED_TEST` and
`Decision-[:ABOUT]`. One of the fifteen planted findings has no question at all.

**Historical runs observe windows their datasets do not cover.** The corpus spans
eight quarters; the datasets declare windows covering only the most recent two.
Nothing reads `Dataset.window`, so no query returns a wrong answer because of it
— but the corpus is not internally consistent, and the honest fix is per-year
datasets rather than a patch.

**Writes are retried without being idempotent.** `Engine.run` retries on 429 and
5xx, and the loader's `CREATE` statements are not idempotent, so a timeout
arriving after a write landed could duplicate rows. Not currently reachable —
`load.py` refuses a non-empty graph and verifies counts at the end — but the
safety comes from the caller rather than from the wrapper.

**No CI.** Nothing runs the generator, the verifier or the suite automatically at
any ref.

**One engine, one version.** Every figure here was read from Samyama Graph 1.1.0
in Docker. Two builds reporting the same version have been observed answering
the same query differently elsewhere in this ecosystem, so treat the numbers as
measured on that build rather than as properties of the engine.

## Usage

```bash
# start the engine
docker run -d --rm --name samyama-demo -p 8080:8080 \
  public.ecr.aws/f9f6l5u4/samyama-graph:1.1.0

# generate the ledger, then load it
python data/generate.py
python etl/load.py --url http://localhost:8080

# ask the catalogue
python -m queries.run --url http://localhost:8080
```

The tests need no engine — they read the committed record and the page:

```bash
python -m pytest tests/ -q
```
